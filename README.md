# agent-gateway

A lightweight daemon that runs on your local machine and securely serves your **Claude** or **Codex** subscription credentials to CI (GitHub Actions, GitLab CI) — so PR reviews run on the subscription you already pay for, without ever exposing the raw credentials.

Built as a companion to [pr-audit](https://github.com/prince-kunwar-xcelore/pr-audit), which runs Claude- or Codex-powered PR reviews in CI.

---

## How it works

```
YOUR LOCAL MACHINE                      GITHUB ACTIONS RUNNER
──────────────────────────────          ──────────────────────────────────────
agent-gateway service (serve)           pr-audit --engine <agent>-cli --auth-token-file …
  reads ~/.claude/.credentials.json       clones agent-gateway
    and ~/.codex/auth.json                runs: agent-gateway decrypt-token --agent <agent>
  serves /token?agent=claude|codex          authenticates (private key or OIDC, see below)
                                            fetches + decrypts credentials
                                            writes them to stdout
                                          claude / codex CLI uses them
                                          posts review back to the PR
```

Credentials are encrypted with **RSA-OAEP + AES-256-GCM** hybrid encryption before leaving your machine, so the tunnel in between (Cloudflare, ngrok, …) never sees them.

### Keeping the login fresh

Served credentials have their **refresh token removed** (Codex: blanked, with `last_refresh` set to now),
so CI can use the access token but can never refresh it. Both providers rotate refresh tokens on use, so a
refresh in CI would otherwise log out the CLI on your machine.

Because CI can't refresh, the gateway keeps the local login fresh itself. When an access token is close to
expiry (Claude: 10 minutes; Codex: 1 day, since Codex refreshes ~2 days before its 10-day tokens expire),
the daemon runs the CLI once with a trivial prompt (`claude -p 'Reply with OK' --tools ''` /
`codex exec … 'Reply with OK'`), which makes it refresh its own credentials file. This costs one tiny
request per refresh (about every 8 hours for Claude). It is rate-limited to one run per 4 minutes per agent.
Claude may leave a token that still has several minutes left unchanged, so the first run doesn't always renew
it; the daemon tries again 4 minutes later (seen in practice: renewed on the second run, within 5 minutes of
expiry). `service logs` shows each attempt.

Credentials expiring within 2 minutes are never served: `/token` returns 503 and `/health` shows the
agent as failing with the reason (e.g. a local refresh that failed because you were logged out). The
service finds `claude` / `codex` through the PATH recorded at `service install`. If you install a CLI
later or move it, run `service install --force`.

### Two auth modes — enable either or both

| | Private key | Allowlist (OIDC) |
|---|---|---|
| Request | `GET /token?agent=…` | `POST /token?agent=…` with `Authorization: Bearer <CI OIDC token>` and `{"publicKey": "<PEM>"}` |
| Who can get credentials | Anyone holding `private.pem` | Only CI jobs from allowlisted repos on the named platform (`--allow owner/*`, `--allow gitlab:group/*`) |
| Encrypted to | Your long-lived `public.pem` | A one-off key generated by that CI job |
| CI setup | `AGENT_GATEWAY_PRIVATE_KEY` secret in every repo | Nothing beyond `AGENT_GATEWAY_URL` (+ `id-token: write` / `id_tokens:`) |
| Revoke a repo | Rotate the keypair everywhere | Remove it from `--allow` |

The allowlist mode verifies the GitHub Actions / GitLab CI ID token against the issuer's published keys (signature, issuer, audience `agent-gateway`, expiry) and checks its `repository` (GitHub) or `project_path` (GitLab) claim against the entries **for that issuer**. A bare `owner/*` means GitHub only: it does not match a gitlab.com namespace that happens to share the name (anyone can register one). GitLab must be allowed explicitly with `gitlab:` or `gitlab@<issuer>:`, and an issuer is trusted only if some entry names it. `decrypt-token` tries the allowlist (OIDC) first whenever the CI job can obtain an OIDC token, and falls back to the private key, if one is configured, when OIDC is unavailable or refused.

## Requirements

- Node.js 20+ (with pnpm) or [Bun](https://bun.sh)
- Linux (systemd) for `service`; macOS LaunchAgent support exists but is untested
- [Claude Code](https://claude.ai/code) and/or [Codex CLI](https://github.com/openai/codex) installed and logged in on your local machine
- A way to reach it from CI: the built-in Cloudflare Tunnel / ngrok helpers, or any port forward / VPN

## Setup (one-time)

### 1. Clone, install, build

```bash
git clone https://github.com/prince-kunwar-xcelore/agent-gateway.git
cd agent-gateway
pnpm install && pnpm build      # the service runs dist/index.js under Node
alias agent-gateway="node $PWD/dist/index.js"   # or: pnpm link --global
```

With Bun installed, `bun src/index.ts …` works too and the service will run the sources directly.

### 2. Configure

```bash
# Allowlist mode (recommended) — only CI jobs from your repos, no keys to distribute
agent-gateway init --allow 'your-user/*'

# …or private-key mode
agent-gateway generate-keys --private-key ~/.agent-gateway/keys/private.pem --public-key ~/.agent-gateway/keys/public.pem
agent-gateway init --public-key ~/.agent-gateway/keys/public.pem
```

This writes `~/.agent-gateway/config.json`. Change it later with `allow add|remove` and
`mode enable|disable` — a running service is restarted automatically.

### 3. Run it as a service

```bash
agent-gateway service install   # systemd user unit (Linux) / LaunchAgent (macOS, untested); starts now + on boot
agent-gateway service status    # service state + per-agent credential health
```

On Linux, starting at boot (before you log in) needs lingering: `sudo loginctl enable-linger $USER`
(`service install` tells you if it's off). The unit only runs `serve --config ~/.agent-gateway/config.json`,
so later config edits never require reinstalling.

### 4. Expose it publicly (optional helper)

The proxy only listens on localhost; any tunnel works. Two are built in, each installed as a second
user service (`agent-gateway-tunnel`):

```bash
# Cloudflare Tunnel — your own domain on Cloudflare; run `cloudflared tunnel login` first.
# Reuses an existing tunnel with the same --name (default agent-gateway).
agent-gateway tunnel setup cloudflare --hostname gateway.your-domain.com

# ngrok — the free plan includes one static *.ngrok-free.app domain; custom domains need a paid plan.
# The authtoken must be in ngrok's config file (ngrok config add-authtoken …), not just an env var.
agent-gateway tunnel setup ngrok --domain your-name.ngrok-free.app

agent-gateway tunnel status | stop | start | remove
```

Cloudflare's helper writes its own `~/.agent-gateway/cloudflared.yml` and leaves `~/.cloudflared/config.yml` alone.
After starting the tunnel, setup checks that `https://<host>/health` is answered by **this** proxy (it compares
the `instance_id` that `/health` reports; start the proxy service first so there is something to compare with).
If something else answers, for example because an existing DNS record for the hostname points at another
tunnel, setup fails and says so. Any failure rolls back: the tunnel service is removed, and the config is
only updated once the tunnel works.
If you point a custom domain at ngrok through Cloudflare DNS, its CNAME must be "DNS only" (grey cloud).

### 5. Add the CI secret

| Secret | Value |
|--------|-------|
| `AGENT_GATEWAY_URL` | Public URL printed by `tunnel setup`, e.g. `https://gateway.your-domain.com` |
| `AGENT_GATEWAY_PRIVATE_KEY` | Private-key mode only: contents of `private.pem` |

Then copy a template from `examples/` (see below).

## GitHub Actions Integration

Pick a template from `examples/` and copy it into your repo. Set `REVIEW_AGENT` to `claude` or `codex` in the template:

| Template | Runtime | Setup time | Build step |
|---|---|---|---|
| `examples/pr-review-bun.yml` | Bun | ~1s | None — runs from source |
| `examples/pr-review-node.yml` | Node 20 | ~30s | None — runs from source via tsx |
| `examples/mr-review-bun.yml` | Bun (GitLab) | ~1s | None |
| `examples/mr-review-node.yml` | Node 20 (GitLab) | ~30s | `pnpm build` (tsup) |

The templates check out agent-gateway and pr-audit at **pinned commits** (the `# pin: … main` lines) and a fixed
Bun version, so a later push to either tool can't change what runs with your credentials until you choose to
update. To move the pins to the current `main` of both tools:

```bash
scripts/pin-review-tools.sh .github/workflows/pr-review.yml   # any number of workflow files
```

Jobs for pull requests from forks are skipped: GitHub gives them no secrets and no OIDC token.

`decrypt-token` prints the credentials to stdout. The templates write them to a 0600 file, mask them, and
pass the file to `pr-audit --auth-token-file`, so they never appear on a command line or in the log:

```yaml
env:
  REVIEW_AGENT: claude   # claude | codex
jobs:
  review:
    permissions:
      pull-requests: write
      contents: read
      id-token: write    # allowlist mode: lets the job request an OIDC token
      checks: write      # pr-audit's neutral "AI review" check when the usage limit is hit
    steps:
      # … checkout + install agent-gateway, pr-audit and the agent CLI (see the templates)
      - name: Fetch agent credentials
        env:
          AGENT_GATEWAY_URL: ${{ secrets.AGENT_GATEWAY_URL }}
          AGENT_GATEWAY_PRIVATE_KEY: ${{ secrets.AGENT_GATEWAY_PRIVATE_KEY }}  # optional fallback
        run: |
          set -euo pipefail
          umask 077
          bun _agent-gateway/src/index.ts decrypt-token --agent "$REVIEW_AGENT" > "$RUNNER_TEMP/agent-auth"
          # mask every line and every JSON string value
          { cat "$RUNNER_TEMP/agent-auth"; echo; jq -r '.. | strings' "$RUNNER_TEMP/agent-auth" 2>/dev/null || true; } |
            while IFS= read -r secret; do
              if [ "${#secret}" -ge 8 ]; then echo "::add-mask::$secret"; fi
            done
      - name: Run PR Review
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          PR_URL: ${{ github.event.pull_request.html_url }}
        run: |
          bun _pr-audit/src/index.ts "$PR_URL" --engine "$REVIEW_AGENT-cli" \
            --auth-token-file "$RUNNER_TEMP/agent-auth"
      - name: Remove agent credentials
        if: always()
        run: rm -f "$RUNNER_TEMP/agent-auth"
```

If `decrypt-token` fails, the job stops at that step with its error instead of reviewing without
credentials. The GitLab templates write the file to `/tmp/agent-auth-$CI_JOB_ID` and delete it in
`after_script` (GitLab can't mask values created at runtime).

`decrypt-token` tries the allowlist (OIDC) first and only uses `AGENT_GATEWAY_PRIVATE_KEY` if OIDC isn't
available or is refused; leave the secret unset for allowlist-only setups. When the agent's usage limit is
hit, pr-audit skips the review with a PR comment and a neutral check instead of failing the job
(GitLab templates: `allow_failure: exit_codes: [3]`).

With `REVIEW_AGENT: codex`, the GitHub templates run `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`
first: Codex reads files only through its bubblewrap sandbox, and Ubuntu 24.04 runners block the user namespaces it
needs. GitLab Docker executors usually block them too; pr-audit then stops with a "Codex's sandbox can't start" hint
instead of reviewing blind.

This repo reviews its own PRs with the same setup (`.github/workflows/pr-review.yml`).

## Operating it

```bash
agent-gateway service status          # is it running, are credentials fresh?
agent-gateway service logs -f
agent-gateway allow add gitlab:my-group/*
agent-gateway allow remove your-user/old-repo
agent-gateway mode enable private-key --public-key ~/.agent-gateway/keys/public.pem
agent-gateway config show
```

Files under `~/.agent-gateway/`: `config.json`, `cloudflared.yml` (if used), the private-key-mode
token cache, and on macOS the service logs. Running `serve` by hand still works and accepts flags that
override the config (`serve --allow owner/* --port 7433`), or no config at all.

If you update Node (e.g. via nvm) or install / move the `claude` or `codex` CLI, reinstall with
`service install --force`: the unit pins the absolute runtime path and the CLI directories it was
installed with.

### Narrowing entries to a workflow, ref or event

By default an entry trusts any job in the repo that can get an OIDC token: any branch, any workflow.
`--require` adds claim constraints to entries; the token's claim must match one of the patterns
(`*` matches any characters, including `/`), and a token without the claim is refused:

```bash
# Only the PR review workflow, only for pull_request events
agent-gateway allow add your-user/repo \
  --require event_name=pull_request \
  --require 'job_workflow_ref=your-user/repo/.github/workflows/pr-review.yml@*'

# GitLab: only merge request pipelines
agent-gateway allow add gitlab:my-group/* --require pipeline_source=merge_request_event
```

They are stored in `config.json` under `allowlist.constraints`, keyed by entry:

```json
"allowlist": {
  "enabled": true,
  "allow": ["github:your-user/repo"],
  "constraints": {
    "github:your-user/repo": {
      "event_name": ["pull_request"],
      "job_workflow_ref": ["your-user/repo/.github/workflows/pr-review.yml@*"]
    }
  }
}
```

Claims: GitHub `ref`, `event_name`, `workflow_ref`, `job_workflow_ref`, `environment`; GitLab `ref`,
`pipeline_source`, `ci_config_ref_uri`. `allow add` with `--require` replaces an entry's constraints;
`allow remove` drops them. Entries are checked independently, so a broader unconstrained entry
(`your-user/*`) still lets everything in that it matches. `allow list` shows the constraints.

Note that on `pull_request` runs the workflow file comes from the PR branch and `job_workflow_ref`
ends in `@refs/pull/<n>/merge`. A constraint on it limits *which* workflow file may ask for credentials,
not what that file contains, so anyone with write access can still edit it in a PR. Constraints narrow
accidental exposure (other workflows, push events, other branches); they don't replace trusting the
repo's writers.

## Encryption scheme

```
encryptToken(rawToken, publicKey):
  aesKey  = random 32 bytes
  iv      = random 12 bytes
  ciphertext, tag = AES-256-GCM(rawToken, aesKey, iv)
  encryptedAesKey = RSA-OAEP(aesKey, publicKey)
  return base64( encryptedAesKey[512] + iv[12] + tag[16] + ciphertext )

decryptToken(encryptedToken, privateKey):
  buf            = base64decode(encryptedToken)
  encryptedAesKey = buf[0:512]
  iv             = buf[512:524]
  tag            = buf[524:540]
  ciphertext     = buf[540:]
  aesKey         = RSA-OAEP-decrypt(encryptedAesKey, privateKey)
  return AES-256-GCM-decrypt(ciphertext, aesKey, iv, tag)
```

## Security notes

- `private.pem` is gitignored and should never be committed
- Private-key mode: `GET /token` requires no auth — the response is encrypted and useless without the private key, which lives only in CI secrets and your local disk (`private.pem`). Anyone with that key and the URL can fetch your credentials.
- Allowlist mode: credentials go only to CI jobs whose OIDC token proves they run in an allowlisted repo **on the platform the entry names** (bare / `github:` entries never match GitLab tokens; gitlab.com and self-hosted issuers are trusted only when an entry names them). Anyone who can change workflows in an allowlisted repo can still obtain them, unless the entry has [claim constraints](#narrowing-entries-to-a-workflow-ref-or-event); GitHub does not issue OIDC tokens to `pull_request` runs from forks.
- OIDC tokens are verified against the issuer's published keys (signature, `iss`, `aud`, `exp`/`nbf`, `kid` required). Unknown `kid`s trigger at most one key refetch per minute per issuer. Request bodies are capped at 16 KB.
- Credentials are encrypted to a key generated by the CI job (allowlist) or to your `public.pem` (private key), so the tunnel never sees them in clear text. In CI the templates write them to a masked 0600 file for `pr-audit --auth-token-file`, never a command line, and check out both tools at pinned commits.
- Raw credentials are held in memory only; the disk cache (`~/.agent-gateway/`) stores the private-key-mode ciphertext.
- Refresh tokens are never served (see [Keeping the login fresh](#keeping-the-login-fresh)): a leaked copy stops working when its access token expires (Claude ~8 hours, Codex ~10 days).
- `/health` is public (it's how `tunnel status` checks reachability) and reports a random per-process `instance_id`, enabled modes, per-agent credential age, access-token expiry, refresh errors and the last local refresh, plus `warnings` (e.g. an empty allowlist). Alert if `ok` is false or `age_seconds` exceeds 3600: credentials are re-read every 15 minutes.
